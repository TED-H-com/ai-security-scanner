## Retained catalog and activation

During preparation, `engines/catalog.json` continued to name the previously published images, versions, provenance and knowledge dates. Each pending plan stored those exact coordinates in closed `previous_artifact` and `previous_publication` records. `upstream_update` contains only the candidate catalog identity; it cannot supply commands, permissions or build inputs. Catalog validation uses it to check the new source recipe while checking the retained published image independently.

The candidate metadata is excluded from executable build identity only after its closed schema is validated, so later removal during activation does not invalidate reuse of the same built bytes. Dockerfile, launcher, source archive and other actual inputs remain identity-bound. Tests reject a substituted retained digest, published candidate, changed source association, non-runnable current engine, hidden executable input and changed package name.

For owner-authorized image distribution, update the fixed version selectors in `scripts/release/verify-publication-artifact.mjs` and its tests to the reviewed candidate tags, then verify both native architectures, signed source/SBOM evidence and anonymous exact-digest retrieval. Then replace catalog identity and dates from the candidate metadata, attach the new publication evidence and remove `upstream_update`. Do not switch the catalog to an unpublished tag. A desktop version/release is a separate owner decision.
